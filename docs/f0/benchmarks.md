## T01 capture replay (`prototypes/capture-commit`)

Synthetic feed: 12 pages of 50 posts with overlapping pages, edited posts on odd pages, and identical text under different IDs.

| Check | Result |
|---|---|
| SIGKILL mid-page, before commit, after commit, on pages 0, 5, and 11 (9 runs) | Pass. Committed pages present, no partial page, no orphan observations, cursor equals the last committed page, an unexpired lease blocks a second owner, resume completes with exact distinct counts. |
| Replay every committed page | Pass. No row changes. |
| Replay a page with a different continuation cursor | Rejected. |
| Skip a page | Rejected. |
| Owner whose lease was taken over tries to commit | Rejected. |
| Page from a different account | Rejected before any write (CAP-02). |
| Same text, different platform IDs | Two sources (Q39). Changed text adds a version. |
| Mutation check | Moving the cursor update into a separate transaction made 6 of the 9 crash tests fail. The suite detects the bug it exists for. |

14 tests pass in about 4 to 6 seconds.

## T11 keyword search (`prototypes/fts5-bench`)

**Corpus**: seeded generator, Zipf-distributed 40,000-word synthetic vocabulary, about 5% Unicode text (accents, CJK, emoji, RTL).

| | |
|---|---|
| Posts | 100,000 (70% short, 25% medium, 5% long) |
| Linked articles | 15,000, chunked at about 1,000 characters |
| Chunks | 216,283 (100,000 post chunks, 116,283 article chunks) |
| Text | 147.6 MB |
| Database file | 629 MB |
| Chunk table | 190 MB |
| FTS5 `unicode61` index | 53 MB |
| FTS5 trigram index (optional) | 361 MB (6.8 times `unicode61`) |
| Build time | load 3.5 s, FTS 5.4 s, trigram 44.7 s |

**Correctness gate** (passed before timing): all 32 non-trashed documents containing a planted token are found, the top 20 are returned, and none of the 5 trashed ones appear (RET-02).

**Method**: 320 queries per run across 8 shapes (rare term, mid-frequency term, common term, two-term AND, phrase, prefix, exact ID, trigram substring). Half add filters (date range and collection membership). bm25 ranking, `LIMIT 20`, trash excluded at query time. One warm-up pass, then 5 timed runs (1,600 timed queries). Cold: 21 fresh processes, each opening the database and running one query.

| Measure | p50 | p95 | p99 | max |
|---|---|---|---|---|
| Warm, all queries | 0.43 ms | 54.9 ms | 82 ms | 196 ms |
| Process-cold first query | 5.3 ms | 54 ms | | 88 ms |
| Process-cold open | 0.89 ms | | | |

Per-run warm p95 ranged from 52.8 to 55.1 ms. Peak RSS was 130 MB. 0 errors.

| Query shape | p50 | p95 |
|---|---|---|
| rare term | 0.28 ms | 0.45 ms |
| mid-frequency term | 1.35 ms | 3.6 ms |
| common term | 40.5 ms | 68 ms |
| two-term AND | 0.23 ms | 0.57 ms |
| phrase | 1.0 ms | 107 ms |
| prefix | 20.6 ms | 58.6 ms |
| exact ID | 0.06 ms | 0.08 ms |
| trigram substring | 0.08 ms | 0.2 ms |

Filtered queries p95 44.8 ms. Unfiltered p95 70.6 ms, max 326 ms.

170 of 1,600 timed queries returned no rows (rare 40, two-term AND 65, phrase 65). These are random term pairs and narrow filters over sparse collections, not misses. The correctness gate covers recall of known documents.

**Limiter**: latency tracks the number of matching rows (Pearson r = 0.88; the slowest query matched 91,000 chunks and took 183 ms). bm25 scores and sorts every match through the joins before `LIMIT`. If needed, ranking inside the FTS subquery before joining would cut this. It is not needed at this scale.

**Verdict**: the PROPOSED T11 keyword target (warm p95 under 1 s) holds with about 18 times headroom on this machine.

**Caveats**

- "Cold" means a fresh process. The OS page cache was not purged (that needs admin rights). True cold-disk numbers are open (see `blockers.md`).
- Measured inside one Node process. IPC and rendering time are not included.
- The production binding is better-sqlite3 (ADR 0002). The SQLite engine is the same family, so the difference should be small, but this is inferred, not measured.
- Synthetic text has a Zipf vocabulary but no real topic structure. Real posts may have different match-count distributions.

## Vector scan (`prototypes/vector-scan`)

Exact top-20 by dot product, 384 dimensions, random unit vectors, single JavaScript thread, 40 queries × 5 runs.

| Vectors | Format | Memory | p50 | p95 |
|---|---|---|---|---|
| 100,000 | float32 | 153.6 MB | 39.8 ms | 64.9 ms |
| 100,000 | int8 | 38.4 MB | 41.2 ms | 69.4 ms |
| 216,283 | float32 | 332 MB | 89.9 ms | 201 ms |
| 216,283 | int8 | 83 MB | 87.4 ms | 150.6 ms |

int8 top-20 overlap with exact float32: 0.97. Random vectors only, so this says nothing about real retrieval quality.

**Limiter**: scalar JavaScript compute, not memory bandwidth (332 MB scanned in 90 ms is about 3.7 GB/s).

**Inferred hybrid latency** at 216,283 chunks: keyword p95 55 ms + vector p95 about 200 ms + query embedding (not measured). The PROPOSED T11 hybrid target is p95 under 3 s.
