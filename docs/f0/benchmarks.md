# F0 benchmarks and prototype results

All results come from synthetic data generated by `prototypes/`. Raw output is in each prototype's `results/` directory. Re-run with the commands in [`prototypes/README.md`](../../prototypes/README.md).

## T01 capture replay (`prototypes/capture-commit`)

Synthetic feed: 12 pages of 50 posts with overlapping pages, edited posts on odd pages, and identical text under different IDs.

| Check | Result |
|---|---|
| SIGKILL mid-page, before commit, after commit, on pages 0, 5, and 11 (9 runs) | Pass. Committed pages present, no partial page, no orphan observations, cursor equals the last committed page, an unexpired lease blocks a second owner, resume completes with exact distinct counts. |
| Replay every committed page | Pass. No row changes. |
| Replay a page with a different continuation cursor | Rejected. |
| Skip a page | Rejected. |
| Owner whose lease was taken over tries to commit | Rejected. |
| Page from a different account | Rejected before any write (CAP-02). |
| Same text, different platform IDs | Two sources (Q39). Changed text adds a version. |
| Mutation check | Moving the cursor update into a separate transaction made 6 of the 9 crash tests fail. The suite detects the bug it exists for. |

15 tests pass in about 4 to 6 seconds. One of them checks that a second job for the same account and collection cannot take a lease while another owner holds one (CAP-03).

## T11 keyword search (`prototypes/fts5-bench`)

**Corpus**: seeded generator, Zipf-distributed 40,000-word synthetic vocabulary, about 5% of sentences carry one non-ASCII snippet (Latin accents, Japanese, Korean, Greek, Cyrillic, emoji). No right-to-left script yet; add Arabic and Hebrew before M3-01's LAN-01 tests.

| | |
|---|---|
| Posts | 100,000 (70% short, 25% medium, 5% long) |
| Linked articles | 15,000, chunked at 1,000 characters with no overlap |
| Chunks | 216,283 (100,000 post chunks, 116,283 article chunks) |
| Text | 147.6 MB |
| Database file | 629 MB |
| Chunk table | 190 MB |
| FTS5 `unicode61` index | 53 MB |
| FTS5 trigram index (optional) | 361 MB (6.8 times `unicode61`) |
| Build time | load 3.5 s, FTS 5.4 s, trigram 44.7 s |

**Correctness gate** (passed before timing): all 32 non-trashed documents containing a planted token are found, the top 20 are returned, and none of the 5 trashed ones appear (RET-02).

**Method**: 320 queries per run across 8 shapes (rare term, mid-frequency term, common term, two-term AND, phrase, prefix, exact ID, trigram substring). Half add filters (date range and collection membership). bm25 ranking, `LIMIT 20`, trash excluded at query time. One warm-up pass, then 5 timed runs (1,600 timed queries). Cold: 21 fresh processes, each opening the database and running one query.

| Measure | p50 | p95 | p99 | max |
|---|---|---|---|---|
| Warm, ranked FTS queries, unfiltered | 2.5 ms | 66.6 ms | 140 ms | 277 ms |
| Warm, ranked FTS queries, filtered | 1.0 ms | 46.3 ms | 66 ms | 175 ms |
| Warm, all 8 shapes pooled | 0.53 ms | 56.4 ms | 103 ms | 277 ms |
| Process-cold first query | 8.0 ms | 91 ms | | 467 ms |
| Process-cold open | 0.92 ms | 1.6 ms | | |

"Ranked FTS" excludes exact-ID lookups and trigram substring queries, which are near-free and would flatter the pooled numbers. All splits come from the same 5 timed runs. Per-run pooled p95 ranged from 51.9 to 63.9 ms. Peak RSS was 123 MB. 0 errors. Load average was 5 to 9 during the run because other work was running on the machine. A run 2 minutes earlier at load 11 to 24 gave a ranked unfiltered p95 of 116 ms. Both pass the target by a wide margin, but contention moves the tail.

| Query shape | p50 | p95 | max |
|---|---|---|---|
| rare term | 0.28 ms | 0.6 ms | 3.0 ms |
| mid-frequency term | 1.4 ms | 3.7 ms | 6.5 ms |
| common term | 40.3 ms | 72.6 ms | 175 ms |
| two-term AND | 0.24 ms | 1.2 ms | 3.2 ms |
| phrase | 1.6 ms | 107 ms | 277 ms |
| prefix | 21.2 ms | 61.0 ms | 213 ms |
| exact ID | 0.05 ms | 0.08 ms | 0.28 ms |
| trigram substring (unranked, unfiltered) | 0.07 ms | 0.16 ms | 5.4 ms |

170 of 1,600 timed queries returned no rows (rare 40, two-term AND 65, phrase 65). These are random term pairs and narrow filters over sparse collections, not misses. The correctness gate covers recall of known documents.

**Limiter**: latency tracks the number of matching chunks. Over the 135 unfiltered ranked queries, Pearson r between match count and median latency was 0.94. The query with the most matches (a phrase matching 91,385 chunks) had a median of 140 ms. Both numbers are in the `limiter` section of the results file. bm25 scores and sorts every match through the joins before `LIMIT`. If needed, ranking inside the FTS subquery before joining would cut this. It is not needed at this scale.

**Verdict**: the PROPOSED T11 keyword target (warm p95 under 1 s) holds on this machine. Judged by the slowest ranked shape (phrase, p95 107 ms) the headroom is about 9 times. The single slowest warm query took 277 ms.

**Caveats**

- "Cold" means a fresh process. The OS page cache was not purged (that needs admin rights). True cold-disk numbers are open (see `blockers.md`).
- Measured inside one Node process. IPC and rendering time are not included.
- The production binding is better-sqlite3 (ADR 0002). The SQLite engine is the same family, so the difference should be small, but this is inferred, not measured.
- Synthetic text has a Zipf vocabulary but no real topic structure. Real posts may have different match-count distributions.

## Vector scan (`prototypes/vector-scan`)

Exact top-20 by dot product, 384 dimensions, random unit vectors, single JavaScript thread, 40 queries × 5 runs.

| Vectors | Format | Memory | p50 | p95 |
|---|---|---|---|---|
| 100,000 | float32 | 153.6 MB | 38.2 ms | 43.0 ms |
| 100,000 | int8 + per-vector scale | 38.8 MB | 39.7 ms | 43.5 ms |
| 216,283 | float32 | 332 MB | 87.2 ms | 144 ms |
| 216,283 | int8 + per-vector scale | 83.9 MB | 84.9 ms | 125 ms |

int8 uses one float32 scale per vector (maxAbs / 127), as ADR 0003 specifies, and multiplies it into each score. Top-20 overlap with exact float32: 0.99 at 100,000 and 0.98 at 216,283. Random vectors only, so this says nothing about real retrieval quality. Load average rose to 23 during the 216k run, which widens its tail.

**Limiter**: scalar JavaScript compute, not memory bandwidth (332 MB scanned in 90 ms is about 3.7 GB/s).

**Inferred hybrid latency** at 216,283 chunks: ranked keyword p95 about 67 ms (worst shape 107 ms) + vector p95 about 125 to 145 ms + query embedding (not measured). The PROPOSED T11 hybrid target is p95 under 3 s.

## T08 backup encryption (`prototypes/backup-age`)

age-encryption 0.3.1 (typage), streaming, random data.

| Check | Result |
|---|---|
| 64 MiB passphrase round-trip | Byte-identical SHA-256. Encrypt 1.35 s, decrypt 1.21 s (about 50 MB/s). Overhead 16,550 bytes. |
| Wrong passphrase | Fails at the header. No plaintext emitted. |
| One flipped byte in the middle of 4 MiB | Fails authentication at the damaged chunk, after 64 KiB of earlier chunks was emitted. |
| Truncated by 70,000 bytes | Fails at the end of the stream, after 256 KiB of authenticated plaintext was emitted. |
| X25519 recipient (unattended schedule path) | Round-trips. |

age authenticates each 64 KiB chunk as it streams, so a damaged or truncated archive can emit a verified prefix before failing. Restore must stage everything and act only after the stream ends without error (ADR 0008).

Not yet covered: restore into a fresh installation, missing media, unavailable destination (M2-08).
